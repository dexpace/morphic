## Findings

### issue: An operation-level requirement that names an undeclared scheme still compiles to "no auth needed". It now gets there through inheritance, and a new test comment claims the opposite
`compilers/openapi/internal/auth/auth.go:206`, `compilers/openapi/internal/auth/auth_test.go` (`TestSecurityRequirement_OperationLevelSoleOptionCollapsesToNil` doc) · rules: `probe-claimed-compiler-behaviour`, `universal-claims-check-every-site`. CLAUDE.md: "A limitation that is deliberately out of scope must be stated in the code and in the PR body".

The commit message frames the defect as: "A requirement that demanded an undeclared scheme was compiling to IR that said the opposite: auth is optional." When an operation's only option is broken, the fix collapses `Operation.Auth` to nil, and nil means "inherit the service default". Whenever that default is `[{}]` or `[]`, the operation ends up with exactly the meaning #41 calls inverted.

```
p1: security: [{}]   ; /x get security: [{missing: []}]
  error openapi/unresolved-ref p1…#/paths/~1x/get/security/0: security requirement references undeclared scheme "missing"
  svc.auth= [{}]
  op op/openapi/paths/~1x/get auth= null      → inherits [{}]: "no auth is one acceptable choice"
p2: security: []     ; /x get security: [{missing: []}]
  svc.auth= []
  op op/openapi/paths/~1x/get auth= null      → inherits []: explicitly public
```
(`morphic compile <spec> -skip-validate`, built at HEAD.)

The test comment says the operation "falls back to inheriting the service default rather than reading as explicitly public". p2 shows that in that case it reads as explicitly public. With no service default (the test's own fixture), the operation carries no auth at all. Its consumer-visible effect therefore matches the old `[{}]`: a client sends no credentials. The IR has no encoding for "unsatisfiable requirement", so the remaining guard is the error diagnostic. That may be the right trade-off, but the code and the commit say the inversion is gone, and they don't state this limitation.

Fix: either pick a lowering that cannot inherit a weaker default (none exists in the IR today, so this probably means a recorded decision), or state the limitation at `auth.go:206` and in the PR body. Also correct the test comment so it no longer claims "rather than reading as explicitly public", and add a case with a service default of `[]` or `[{}]` that pins whichever behaviour is chosen.

### issue: A `null` security entry still lowers to the empty-option encoding. That is the same "broken requirement becomes no-auth-is-fine" mechanism, at the branch this commit edited and newly pinned
`compilers/openapi/internal/auth/auth.go:224-226`, `auth_internal_test.go` (`TestLowerSecurityRequirement_Nil`) · rules: `invalid-never-lowers-as-valid`, `sweep-sibling-code-sites`. CLAUDE.md: "a defect is a property of its *mechanism* … Sweep every site of the mechanism before closing it."

```
p11: security: [~]
  error openapi/validation/validation-type-mismatch p11…#4:5: … openapi.security.0 expected `object`, got `scalar`
  svc.auth= [{}]
p12: /x get security: [~]
  op op/openapi/paths/~1x/get auth= [{}]
p5:  security: [{missing: []}, ~]
  svc.auth= [{}]        ← the broken option drops; the malformed null survives as "no auth is acceptable"
```

The commit changed this branch to `return ir.AuthRequirement{}, true, nil` and added `assert.True(t, ok, "a nil requirement entry is not a resolution failure")`. That pins a malformed entry (one the validator itself rejects) as a valid "no auth is one acceptable choice" option. This is the inversion the commit exists to remove, through a different input spelling (`probe-every-source-spelling`). Mutant M8 (nil → `ok=false`) reddens only that assertion, so nothing else depends on the current choice.

Fix: treat a nil entry like a broken one (`ok=false`, so it drops with a diagnostic at its `/security/<i>` pointer), and flip the internal test. Or, if keeping it is deliberate, say why in the code.
