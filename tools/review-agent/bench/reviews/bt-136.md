## Findings

### issue: Validate still panics on a typed-nil `*ir.Model` when a model discriminator's mapping names it, so the class the commit says it closes is still open
`pass/validate.go:270-275` (`isSubtype`) · rule: `sweep-every-site-of-the-mechanism` / `no-panic-on-nil-or-zero`. CLAUDE.md: "a defect is a property of its *mechanism* … Sweep every site of the mechanism before closing it"; pass/doc.go: "spec-level problems surface as [ir.Diagnostic] values, never as panics".

The commit screens nil entries only where a check **iterates** `doc.Types` (`liveTypeIDs`). It does not screen where a check **looks one up by ID**. `isSubtype` does `sub, ok := doc.Types[target].(*ir.Model)` and then reads `sub.Base`. A typed nil passes that comma-ok, which is the exact mechanism the commit message describes. `mappingTarget` reaches it after `_, declared := doc.Types[target]` accepts the nil entry as declared.

Probe: an external test in `pass` built on `validDoc()`. It sets `t/m.Discriminator = {PropertyName: "k", Mapping: {"x": "t/nil"}}` and `doc.Types["t/nil"] = (*ir.Model)(nil)`, then calls `pass.Validate(doc)`:
```
model-discriminator->typed-nil-model: PANIC: runtime error: invalid memory address or nil pointer dereference
  pass/validate.go:275   (isSubtype: sub.Base)
  pass/validate.go:262   (mappingTarget → member)
  pass/validate.go:242   (checkMapping)
  pass/validate.go:224   (checkModelDiscriminator)
  pass/validate.go:192   (checkDiscriminators)
  pass/validate.go:29    (Validate)
```
I swept the other `doc.Types[...]` sites (`git grep -n 'Types\[' -- pass/*.go ':!pass/*_test.go'`):
- `:157` and `:173` are the screens themselves.
- `:188`, `:291` and `:401` are now screened by `liveTypeIDs`.
- `:259` is `mappingTarget`, which treats a nil entry as declared and so forwards it to `:271`.
- `:271` is `isSubtype` and is **unscreened** (the panic above).
- `:435` is `graphqlReachableTypes`. I probed it with a GraphQL-bound operation whose parameter targets a nil `*ir.Model`, a nil `*ir.List` and an untyped nil. None panicked, because the reflection walk tolerates a nil pointer.

The union arm with a typed-nil mapping target is clean: it reports `ir/nil-type` plus `pass/discriminator-missing-variant`. `isSubtype` is unchanged by the diff, but the diff claims to fix this mechanism for `Validate` as a whole. The commit says a nil `*ir.Model` "panicked the pass" and that screening at the iteration helper means "a check added later inherits the guard". The test comment rejects a guard "scoped to the site rather than the mechanism". So this site is in scope.

The new test cannot see it: no fixture places a nil entry at a discriminator mapping target. Planting the one-line guard `if !ok || sub == nil {` in `isSubtype` leaves `go test ./pass` green, so nothing pins the site either way.

Fix (removes the class, not the instance): route every read of a `doc.Types` value through one accessor that treats a nil entry as absent. For example, `typeAt(doc, id) (ir.TypeDef, bool)` returns `false` when `isNilTypeDef`, and both `liveTypeIDs` and `isSubtype` use it. Add a test row where the nil `*ir.Model` is a mapping target of a model discriminator, and also of a union discriminator, which today is clean but unpinned.

### issue: the new comments and the commit body state counts and universals that the code contradicts
`pass/validate.go:133-136, 146-152, 165-169` · rule: `universal-claims-enumerate-every-site`, `no-maintained-counts-or-state-in-prose`. CLAUDE.md: "Derive counts; never maintain them."

- `checkNilTypes` says Validate "dereferenced the **four kinds** it did match". Only two kinds were ever matched, `*ir.Union` and `*ir.Model`. The new test's own comment says so: "not just the two whose dereference was observed to crash".
- The commit body says "**four checks** matched one and dereferenced it" and then names three (`checkDiscriminators`, `checkDuplicateWireNames`, `checkArgsOutsideGraphQL`). The fourth site of that mechanism is `isSubtype`, and it is the one left unfixed (finding above).
- `isNilTypeDef` says "**every** walk over doc.Types screens entries through this first". `checkDanglingRefs`' reflection walk (`collectRefs(doc, "doc", …)`) and `graphqlReachableTypes` both read `doc.Types` without it, and `isSubtype` is a read that should.
- `liveTypeIDs` says "**Every** check that iterates doc.Types dereferences the value it matched". `checkNilTypes` and `checkDanglingRefs` iterate it without dereferencing.
- `liveTypeIDs` also says "a check added later inherits the guard" (and the commit says the same). That holds only if the later check calls `liveTypeIDs` and not `sortedKeys(doc.Types)`, which is the idiom every other registry walk in the file uses. Nothing enforces it. The claim would hold if the screening sat on the read rather than on one of two iteration helpers, which is the accessor in the fix above.

Fix: drop the number (or say "the Model and Union arms"), and scope "every walk" / "every check" to the checks that call `liveTypeIDs`. Once the accessor exists, say instead that every read of a `doc.Types` value goes through it.

### nit: the `ir/nil-type` pointer is spelled neither of the ways `diag`'s contract allows
`pass/validate.go:178` · rule: `diagnostic-provenance-names-the-real-site`.

`diag`'s doc comment says the pointer is "a stable ID, or a path through the document's own fields as the reference walk spells it". Probed in one document, the walk spells the registry `doc.Types[t/m].Properties[0].Type.Target` (`ir/dangling-type-ref`), while the new diagnostic is `types[t/nil]`. That copies irverify's `Violation.Path` (`ir/irverify/irverify.go:64`). Matching irverify is defensible: one code, one location spelling. If that is the choice, then `diag`'s comment is the thing that is now wrong and should name it. Otherwise use `doc.Types[<id>]` or the bare ID `t/nil`, as `checkDuplicateWireNames` does.

### suggestion: the new per-kind table is a hand-written kind list nothing holds to the kind set
`pass/validate_test.go:202-215` · rule: `derive-lists-from-their-source`. CLAUDE.md requires "a switch-completeness test over the kind enum".

The map lists 11 typed-nil kinds plus untyped nil. At this revision the only completeness tests are `ir/typedef_test.go`'s `allKinds` and `TestTypeDef_KindDispatchIsComplete`, and neither sees this list, so a new `TypeDef` kind would silently go unexercised here. The production screen uses reflection and is kind-agnostic, so the cost is coverage drift rather than a live bug. One way to derive the rows: build them from `ir.NewTypeDef(kind)` over every kind (the decoder's dispatch already does this), with `reflect.Zero(reflect.TypeOf(td))` giving the typed nil.

### suggestion: `isNilTypeDef` now exists twice, byte for byte
`pass/validate.go:137-143` and `ir/irverify/irverify.go:108-114` · rule: `parallel-implementations-agree`.

The layering keeps `pass` and `irverify` from importing each other, so the only shared home is `ir`. The two copies agree today, and both checkers report `ir/nil-type` for the same entries. Nothing ties them together, though, and the "one defect, one code, whichever checker a caller runs" rule in `pass/doc.go` depends on them agreeing. This is low priority, but worth a line in the commit or the code saying the duplication is deliberate.

## Probed and clean
- The base reproduces the commit's claim. With `pass/validate.go` at `861fe727ae^`, every subtest of the new test fails with no diagnostics at all (`[]string{}`), and the `model`/`union` rows fail too.
- Union discriminator with a typed-nil `*ir.Model` mapping target: no panic; reports `ir/nil-type` and `pass/discriminator-missing-variant` ("is not a variant of it").
- A GraphQL-bound operation whose parameter targets a nil `*ir.Model`, a nil `*ir.List` or an untyped nil: no panic, one `ir/nil-type` each. `graphqlReachableTypes` → `appendTypeIDs` tolerates a typed-nil root.
- Two nil entries (`t/nil` typed, `t/nil2` untyped) alongside a dangling ref: one `ir/nil-type` per entry, in sorted order, and the dangling-ref check is unaffected.
- `checkNilTypes` runs first in `Validate`, which is consistent with "most-structural first".
- Every `TypeDef` implementer has a pointer receiver (`git grep 'func (.*) typeDef()' ir/` lists 11, all `*T`). The reflect-based screen is complete for the sealed set, and `Channels`/`Auth` are value maps, so they cannot hold a typed nil.
- A JSON `null` entry in `types` cannot reach `Validate` through the decoder: `TypeRegistry.UnmarshalJSON` rejects it as an unknown kind `""`. The nil entry is reachable only from Go-built documents, which is what the test builds.
- Each of the three `liveTypeIDs` call sites is load-bearing on its own (mutation table).
- Layering is unchanged: `pass` adds only stdlib `reflect`, which `pass/refs.go` already uses.
- New functions are well under the caps, the new doc comments are under 100 words each, and the commit body has no session or audit framing.
