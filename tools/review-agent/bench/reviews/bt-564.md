## Findings

### issue: the new normative sentence in ir-design.md, and targetHint's lead, are false for a `$ref` to a position outside /components/schemas
`docs/ir-design.md:485`, `compilers/openapi/internal/schema/compose.go:1121` (targetHint), `:1159` (refHint) · rule: `universal-claims-enumerate-every-site`, `limitation-stated-in-code`

The doc now says: "The alias's name hint is the hint the node the `$ref` resolves to carries — a component's name, or, for a position inside a schema, the hint its own declaration gives it". targetHint says it returns "the hint of the node the reference resolves to, so a union variant and an allOf branch are named as the type they hold". Neither is true when the target sits under /paths, because there positionHint declines and refHint falls back to the last token. refHint's own doc says so, but the two universal statements above it do not.

- `probe/p10_allof_paths_alias.yaml` is the exact shape the ir-design paragraph describes: `X: {allOf: [{$ref: '#/paths/~1b/get/responses/200/content/application~1json/schema/items', description: narrowed}, …]}`. Output: `t/anon/components/schemas/X/allOf/0 scalar items base=…/schema/items`, but the target node is `…/schema/items model response_item`.
- `probe/p1_paths_variant.yaml` does the same with a union variant. The variant hint is `items` and its `Type.Target` node is `response_item`.
- Both specs pass `morphic-harness` (`ok`), so this is about naming, not order. The row "a pointer outside components falls back to its last token" in `TestRefHint_Shapes` pins exactly that behaviour.
- #529 tracks only the /paths *subtree* order dependence. Nothing in the commit, in the code, or in the tracker before 2026-09-26 records that #521's guarantee stops at /components/schemas.

Fix:
- Scope both sentences to targets under /components/schemas, and name the /paths fallback (the last token) where the guarantee is stated.
- File the remainder and use `Refs #521` rather than `Closes #521` if the PR body closes it. That part is conditional on a PR body I cannot see.

### issue: maxTargetHintHops' stated reason is false — a legal 70-link branch chain reaches the cap, compiles clean, and is silently named by the ordinal #521 removed
`compilers/openapi/internal/schema/compose.go:1115-1119` · rule: `verify-the-stated-reason`, `bounded-walk-reports-truncation`

The comment says: "A chain of pure references is refused before lowering (the cycle scan), so reaching the cap means a document the scan let through, not legitimate depth."

Probe (`probe/p4_chain70.yaml`): `X0..X69`, each `{oneOf: [{$ref: '#/components/schemas/X{i+1}/oneOf/0'}, {type: integer}]}`, with `X70: {oneOf: [{$ref: T}, …]}`.
- `morphic compile -skip-validate`: exit 0, 0 diagnostics. `morphic-harness`: ok.
- The hints on the `…/oneOf/0` nodes break down as `64 t`, `6 variant_0`. X0's variant is `variant_0`, while the 10-link control (`p4_chain10`) gives all `t`.
- Only a real cycle is refused: `p4_cycle.yaml` gives `openapi/cyclic-ref` with exit 1.

So the cap is reachable by legitimate depth, and when it is hit the name falls back with no diagnostic. The tests reach a depth of 3 (M13 `=2` reddens `TestUnionVariant_IsNamedAsTheNodeItHolds`). Nothing tests at the boundary.

Fix:
- Correct the comment: a chain longer than the cap is named by the hop it stops at.
- Or bound it the same way resolve's `maxRefChain` is bounded, and surface it.
- Add an at-, below- and above-cap case.

### question: is a duplicate variant hint within one union acceptable?
`compose.go:1062` (branchHint → targetHint)

A `$ref` to another union's inline branch is now hinted `variant_N`, which can equal a sibling's own positional hint. `probe/p18_dup_variant.yaml` (`Choice: oneOf: [{inline object}, {$ref: X/oneOf/0}]`):
- parent: `["variant_0","0"]`
- HEAD: `["variant_0","variant_0"]`

Validation is clean and the harness says ok. ir-design.md has no uniqueness rule for `Variant.Name`, and the parent build could already collide (two `$ref`s to `…/items`). The change trades those collisions for this one. Worth deciding on purpose rather than as a side effect of #521.

## Equivalent mutants and declined findings
- M10b (`ok && !branch`) is equivalent: an inline branch falls through to the same `if ok` return.
- M10c is equivalent; it is reported above as the redundant branch.
- M8 (composition arm without `isDecimalIndex`): a non-decimal child of oneOf/anyOf/allOf is not a schema position, so no resolvable `$ref` reaches it.
- M20 (subSchemaHint's targetHint → refHint) is equivalent for order: the node at the pointer is renamed by the declaration (provisional) or takes the recorded hint in both orders, and a pure `$ref` position has no subtree. It changes only the names of nodes that only a reference reaches.
- M12b (drop the whole positionHint check in referencedBranch) is subsumed by M12.
- `declared` is last-write-wins while Intern is first-write-wins. They would disagree only if two declaration visits gave one coordinate different hints. I found no such input: response, pathItem and path-parameter mounts all derive from the declaring coordinate (p5, p6, p11, p12). Declined.
- `declared` records hints that are never read where the declaration interned a node; the doc says so. The cost is one map entry per declared position, and moving the record would not shrink it, because the entry-point call runs before the intern. Declined.
