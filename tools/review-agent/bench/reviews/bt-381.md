## Findings

### issue: max-merge lets a stale cached fragment cover a block that the run go test reports left uncovered, so after `go clean -testcache` the gate can pass at 100% while go test prints 66.7%
`scripts/check-coverage.sh:39-42, 47-51, 65-67` · rules: catalog `justification-must-be-load-bearing` ("a correct verdict does not validate a false reason") and `universal-claims-check-every-site`; CLAUDE.md "Probe, don't read."

The comment justifies max with "the repeats are one run's data re-emitted". That is false for the very case the commit names. In cmd/go (`test.go` `tryCacheWithID`, go1.26.3 lines ~1935-1944, same order in go1.27.2), the fragment appended at each key comes from the **previous, cached** run. It is appended before the expiry check rejects it. The third copy is the fresh run. So after `go clean -testcache` the profile holds two copies from the old run and one from the new run. Morphic itself shows this. In the expired profile, two blocks in `internal/harness/order.go` differ between the copies:
```
order.go:185.49,185.95 1 16   (cached, key 1)
order.go:185.49,185.95 1 16   (cached, key 2)
order.go:185.49,185.95 1 14   (fresh run)
```
Taking the max across runs means any block the old run reached counts as covered, whatever the reported run did. The "deliberate consequence" paragraph calls the old behaviour a "false failure". In this case the old failure was the true verdict for the reported run.

To probe it I built a scratch module (`p.F(b bool)`). Its test reaches the `b` branch only when a file exists, and checks for the file with `syscall.Stat`, which the test log does not record. That stands in for a subprocess, the clock, go-cmp's deliberate randomness or a race. Run 1 with the file present. Then delete the file, run `go clean -testcache`, and run the HEAD script:
```
ok  	example.com/probe/p	0.004s	coverage: 66.7% of statements
Coverage gate passed: all 3 statements covered.
```
Profile: the `p.go:6.7,8.3` block shows `1 1`, `1 1` (cached) and then `1 0` (fresh). On the same profile file, the BASE script prints `Coverage gate failed: 1 of 9 statements uncovered` (exit 1) and the HEAD script prints `passed` (exit 0). With `GOFLAGS=-count=1`, which skips the cache lookup and so writes one copy, HEAD correctly prints `1 of 3 statements uncovered`. So `go clean -testcache`, the usual way to force a fresh verdict, no longer gives one, and the gate and go test's own summary line now disagree in a single log.

Scope: on morphic at 5d7ac495, no block flips between 0 and non-zero across copies; the only differing blocks are the two above, both non-zero. So this tree passes for the right reason. The defect is in the mechanism, not in a current false pass.

Fix: merge by **last occurrence**, not max. Per package, cmd/go appends fragments one after another under one lock: key 1, then key 2, then the run. It stops at the first one it accepts, so the last copy of each block always belongs to the run go test reported. In the awk, replace `if ($3 + 0 > count[$1]) {` with an unconditional `count[$1] = $3 + 0` (keep the NumStmt conflict check). I ran that variant: on the probe profile it gives `1 of 3 statements uncovered` (correct). On morphic's expired and warm profiles it gives `all 4942 statements covered` for both. Then rewrite the two paragraphs at lines 39-49 to state the real premise: the earlier copies are a previous run's, and the last one is the run reported.
